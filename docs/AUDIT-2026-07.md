# ferroDAC Architecture & Performance Audit — July 2026

*Method: 14 parallel subsystem audits (11 planned + 3 coverage-critic gap fills) over the
full codebase (23,786 lines), four lenses per audit (abstraction/interfaces, GUI-thread
blocking, unnecessary data loading, stack foundations), with every medium+ finding
adversarially verified against the code by an independent agent, and micro-benchmarks run
where numbers matter. 149 findings: **102 confirmed, 20 partially confirmed (correction
noted), 0 refuted**, 27 low/unverified. Detailed evidence in the appendix; every claim
carries a file:line.*

---

## Executive summary — the four questions answered

**1. Do we have the right level of abstraction with proper interfaces?**
Mostly yes — and that is worth saying clearly: the *vocabulary* layers are genuinely
good. Reading/Source/Sink/Device, the SourcePort/SinkPort patch-bay, the tiered
resolver (RAM/Zarr/hub behind one coverage/query protocol), the Widget-vs-Panel split,
tags/projects as meta-only overlays — all clean, Qt-free, and faithful to DESIGN.
Verdicts: 13 of 14 subsystems "mostly-sound"; only the app shell is "needs-work".
**The missing abstraction is not a data model — it is an execution model.** No contract
in the system says *where code runs*: Bus sinks, resolver tiers, processors, and device
calls all execute on whatever thread invokes them, which in practice is the GUI thread.
That one gap produces the majority of the 60 blocking findings, and it is also a plugin
liability: a third-party sink doing 50 ms of work would freeze every install that loads
it.

**2. Is the app free of bolted-on ad-hoc fixes?**
Largely, with three concentrations of debt: (a) the ~2,100-line `MainWindow` in
`app.py` has absorbed domain policy (recording lifecycle, export orchestration,
provenance freezing, git policy) that DESIGN §4.1 assigns to Qt-free layers, and it
reaches into `dashboard._panels`/`panel._curves` privates, undermining the versioned
Widget contract; (b) glue-layer accretion — ProjectNavigator takes 18 constructor
callbacks, HubController hand-wires 8 services per connect, the reliable-LWW channel is
copy-pasted twice on the hub and the reconnect state machine five times on the client;
(c) several "synchronous for now" placeholders (replay re-stream, exports, git) that
were never revisited and now sit on the hot path.

**3. Where does the app freeze, and why is it slow after a week?**
The week-long-streaming slowdown is **fully explained and quantified** — it is not a
mystery and not a stack limit. Four compounding mechanisms, all confirmed (details and
numbers in §2): unbounded grow-mode chart buffers with O(history) re-conversion per
reading; the Zarr store writer (appends + O(history) rollup rebuilds) running inside
the GUI-thread engine drain; the Timeline rescanning the whole store catalog 2–3× every
500 ms; and the every-2-s full-heap `gc.collect()` whose cost grows with exactly the
objects the first mechanism accumulates. Separately, ~60 catalogued freeze points
(§3) show where explicit user actions block the GUI thread — from 65 ms store flushes
to minutes-long exports, git pushes, and library downloads, almost all with no feedback.

**4. Have we hit the technological limit of the stack?**
**No — nowhere near.** Measured: Zarr windowed rollup queries are 4–12 ms even at 6M
samples/source; pyqtgraph has ≥25× headroom once buffers are windowed (a screen needs
the resolver's 2–4k-point envelope, not 6M raw points); Python protobuf/gRPC conversion
has ≥1000× headroom (543k scalar conversions/s vs a few hundred needed); JSON overlay
stores are fine to ~50k tags. Every ceiling that bites today is a *usage pattern*
(1 MiB append chunks, from-scratch rollup rebuilds, full-epoch timestamp reads,
per-reading setData) — each with a straightforward fix. **No component swap is needed
or foreseeable for the target workload.** The one real constraint to design around is
the GUI thread itself, plus one platform invariant: Qt object finalization must stay on
the GUI thread (the gc.disable() regime), which every "move it off-thread" fix below
must respect.

## 2. The week-long slowdown — the confirmed causal chain

All four mechanisms confirmed with measurements; together they saturate the GUI thread
as a function of *session age*, which is why even unrelated actions feel slow.

| # | Mechanism | Where | Measured cost | Growth |
|---|-----------|-------|---------------|--------|
| 1 | **Grow-mode default + per-reading `setData` on Python-list buffers.** Charts default to "window = [launch, now]", `trim_live` is a permanent no-op, and `ChartPanel.feed` re-converts the FULL buffer per reading | `app.py:2242`, `panels.py:399-410` | setData: 0.6 ms @10k pts → 105 ms @1.2M pts, *per reading per curve*; ~0.5 GB RAM per 6M-pt curve | O(history) per reading |
| 2 | **StoreWriter runs on the GUI thread** via the engine drain: each 2-s flush is an 8 MB tail read-modify-write (1 MiB chunks) + an uncached chunk-0 read; every 50k samples the rollup pyramid is rebuilt from the FULL epoch | `writer.py:109/147`, `zarrstore.py:29/227/238` | flush: 65–110 ms per source per 2 s (at ≥0.5M samples); rollup rebuild: 0.22–0.31 s @6M samples, recurring — total rollup work is O(N²/50k) | O(history), recurring |
| 3 | **Timeline live tick rescans everything**: full store catalog 2–3× per 500 ms tick + per-source coverage (and with a hub: 2 synchronous RPCs per source per refresh) | `timeline.py:688`, `readtier.py:53` | 43 ms/tick @8 sources/5 epochs → 615 ms/tick @60 sources/100 epochs | O(sources × epochs) per tick |
| 4 | **Full-heap `gc.collect()` every 2 s on the GUI thread** (the segfault fix — the *invariant* is right, the *policy* is stronger than needed): cost scales with live objects, which mechanism #1 grows without bound | `diagnostics.py` (gap-fill audit) | 14.6 ms @100k live objects → 324 ms @3M, GIL held throughout (acquisition threads jitter too) | O(live heap) per 2 s |

Compounding effect: any stall makes the next `Bus.drain` batch bigger (no batch cap),
which makes the tick longer — a death-spiral amplifier (`bus.py:58`, confirmed).

**The fix pattern** (one abstraction change + three bounded fixes, no redesign):
1. **Give the Bus/engine an execution contract** — `subscribe(sink, thread='gui'|'worker')`
   with a platform-owned worker pump; only actual widgets stay on 'gui'. This single seam
   retires mechanism #2, the processor/agent-feed/writer blocking class, and hardens the
   plugin SDK before third-party sinks proliferate. (CVRunner in vision/ is the in-repo
   precedent to copy: QThread scheduler + bounded pool + at-most-one-in-flight.)
2. **Bound the chart path**: numpy ring buffers, one `setData` per batch (not per
   reading), switch curves to the resolver's decimated envelope query beyond ~50k visible
   points. pyqtgraph then has 25× headroom.
3. **Fix the write path's cost model**: 8–64k-sample chunks (kB-scale tail appends),
   cache `t0`, make rollups incremental (fold only new samples, O(new) not O(total)).
4. **Soften the GC policy without touching the invariant**: gc.freeze() after startup,
   generation-limited ticks, duration logging, adaptive cadence — and write the
   invariant into DESIGN so off-thread refactors and plugin authors respect it.

## 3. The responsiveness milestone — catalogued freeze points

The audit catalogued ~60 GUI-thread blocking paths (full list with triggers/durations in
the appendix). They cluster into five tiers; the tier structure is the suggested work
order because the first two make the rest cheap.

**Tier 0 — the enablers (do first)**
- Bus/engine thread-affinity contract (above) — retires the always-on writers.
- One **async resolver entry point** (queued query + coverage-TTL cache): every UI read
  (Timeline, replay, export, hub tier) goes through it off-thread; the tier protocol
  itself can stay synchronous. Retires the "4-s-timeout synchronous RPC on the paint
  thread" class (`readtier.py:53`, `resolver.py:159`).
- A single reusable **worker+progress pattern** ("what / why / how long, cancellable")
  — the UI mechanism every tier below plugs into. Today's feedback is a wait cursor at
  best, `processEvents` pumping at worst (`app.py` park/scrub).

**Tier 1 — always-on costs (the week-long fix, §2)**

**Tier 2 — frequent user actions that freeze today**
- Park/scrub/jump/go-live: synchronous full-res window re-stream, one Python `Reading`
  per raw sample — 1.5 s/1M samples, 4–10 s for a day-window, minutes for grow-mode
  weeks (`replay.py:293`). → worker thread + envelope-first display.
- Timeline window commit (drag/double-click/Fit): synchronous full re-query.
- Recording stop & startup crash-recovery: whole-span CSV export inline — ~30 s+ after
  a week (`app.py:3800`); also fires at launch after a crash, delaying startup.
- Device option changes & session restore bypass `async_config` and run driver serial
  I/O on the GUI thread (`manager.py`).

**Tier 3 — occasional actions, worst absolute durations**
- Git: push ≤120 s, clone ≤300 s, commit unbounded — on the GUI thread, some fired
  from timers (`projectgit.py` call sites). Backup zips likewise.
- Extension "Add from git": clone/fetch + imports inline. MoNA library download +
  MSP parse: **minutes**-long freeze (`analysis/library.py`).
- Hub connect: synchronous `ListSources` (incl. launch autoconnect); backup-folder
  browser: up to 10–120 s timeouts; project-zip download inline.
- OCR preview, window plot-export, report render: seconds-scale inline work.

**Tier 4 — hub-side responsiveness** (viewers judge the system by it)
- Store servicer runs blocking Zarr I/O on the hub event loop — one slow historic query
  stalls *every* live stream (`service.py`; the Backup servicer already shows the
  correct run-in-executor pattern).
- Hub never builds rollups on synced data → every hub Query scans raw full-res history.
- `PushChunk` applies trace rows one at a time (two Zarr resizes + attr rewrite per row).
- `publish_project`: synchronous Gitea HTTP (≤3×15 s) + `shutil.rmtree` on the loop.

## 4. "Do we load data we don't strictly need?" — confirmed, in five places

Your suspicion is right. Ranked by cost:
1. **Charts ingest full-rate history instead of querying the windowed view.** DESIGN
   §7.2 says the windowed query interface is "the only way panels read data" — the main
   dashboard doesn't use it; it accumulates raw readings forever (the #1 mechanism).
2. **Full-epoch timestamp reads for any window**: `read_raw`/level-0 `query` load the
   entire epoch `t` array (48 MB at week scale) to serve a 10-minute window
   (`zarrstore.py:288/405`). Timestamps are monotonic — binary-search the chunk
   boundaries instead.
3. **Poll-and-rescan catalogs**: store `sources()` every 500 ms, `epoch_lengths()` every
   5 s over ALL epochs ever, coverage every 2 s — no change notification, no caching,
   cost grows with store age forever.
4. **Full-state exchanges in net/**: `GetSyncState` returns every (source, epoch) ever
   each 5 s; `WatchTags` replays the entire tag history (tombstones included, never
   compacted) on every reconnect; hub connect pushes every local marker as one RPC each.
5. **Replay/park re-streams full resolution** even when the consumer is a chart that
   will decimate to ~4k points anyway.

Also confirmed as *good*: lazy QtWebEngine/docs creation, bounded log view, bounded
waterfall scan cap, camera/vision pipeline all bounded — the discipline exists in the
codebase; it just isn't uniform.

## 5. Foundations — measured ceilings vs. actual needs

| Layer | Measured ceiling (this machine) | Current need | Headroom |
|-------|--------------------------------|--------------|----------|
| Zarr windowed rollup query | 4–12 ms @6M samples/source | per refresh | ✓ fine |
| Zarr append (fixed chunking) | ~kB/s writes cost 65–110 ms today; with 8–64k chunks: sub-ms | ≤400 samples/s ≈ 3 kB/s | ~10⁵× after fix |
| pyqtgraph line curves | 100–200k pts/curve @10–20 fps; screen needs 2–4k envelope | few curves, 1–50 Hz | ≥25× |
| protobuf/gRPC conversion | 543k scalar conv/s; 3.3 ms per 5000-reading batch | few hundred/s | ≥1000× |
| JSON overlay stores (tags etc.) | 12 ms rewrite @10k tags; fine to ~50k | 10²–10⁴ | ✓ (compact tombstones eventually) |
| Per-sample Python objects (Reading) | ~0.5–0.6M objects/s creation | few hundred/s | fine until kHz waveforms — DESIGN §11's block modality already covers that regime |

**Verdict: keep the stack.** PySide6 + pyqtgraph + Zarr + gRPC are all orders of
magnitude below their ceilings for the target workload (few devices, 1–50 Hz, weeks-long
runs, several viewers). The binding constraint is GUI-thread placement and a few wrong
cost models, all fixable in usage. The first genuine ceiling on the horizon is per-sample
Python object churn *if* kHz waveforms are ever pushed sample-wise — the already-planned
block/waveform modality (DESIGN §11) is the right answer; worth a DESIGN note anchoring
it to these numbers (~0.5M objects/s).

## 6. Architecture debts worth scheduling (beyond performance)

**Platform contracts (protect the extension story):**
- **The plugin SDK cannot express a driver**: `ferrodac.plugin` says "import ONLY from
  here" but exports neither `BaseDevice` nor Source/Sink/Option/Param — real drivers pin
  to `ferrodac.core` internals, defeating the API_VERSION gate. Export the driver
  vocabulary (and the threading rules) through the SDK.
- **Device threading contract**: drivers are called from 4+ threads; the TPG driver
  invented its own lock, the QMS its own write queue, the Keithley never reconnects.
  Platform should own a per-device serialized executor; BaseDevice should own
  discovery caching + reconnect policy (today triplicated, divergent).
- **Processor contract half-dead**: `process()` runs on the GUI thread, dispatch only
  fires for Trace values (registered float/bool processors never execute), `outputs()`
  is materialized once. Fix with the Bus affinity work (Tier 0).
- **Widget contract completeness**: input widgets need an undeclared `emitted` signal;
  `attach_session`/`set_cursors`/`set_processor_host` are hasattr side-channels; the SDK
  dtype vocabulary omits image/action/enum that the router actually uses. Fold these
  into the versioned contract before third-party widgets exist.
- **MainWindow decomposition**: extract the Qt-free domain policy first (recording
  lifecycle → L2 service, export orchestration, provenance capture) — that is also what
  the worker+progress pattern needs anyway; the dialog/wiring cleanup can follow
  gradually.
- **Hub: extract the reliable-LWW-tombstone channel** (tags and projects are the same
  code twice; DESIGN §18 plans more record types). Client: collapse channel-per-concern
  into one resilient session hosting per-concern streams (deletes 5 copies of the
  reconnect FSM — this week's outage lived in exactly that duplication).

**Correctness/safety flags found along the way (small but real):**
- **Gitea admin token is embedded in clone URLs** fanned out to clients, persisted in
  project.json, mirrored into backups and downloaded zips. Rotate + move to a
  per-project deploy credential or the reserved auth seam (DESIGN §13).
- **QMS queued control writes**: filament OFF waits for the current sweep to finish
  while the UI already shows OFF — surface pending state, and consider an abort lane
  for safety-relevant sinks.
- **Doc-room compaction is never invoked by any client** (hub supports + e2e-tests it):
  room logs grow per keystroke forever and a hub restart loses everything since the
  seed. One client call + leader signalling finishes the designed protocol.
- **Backup dirty-tracking misses doc writers** — collaboratively edited docs aren't
  mirrored until some other change dirties the project.
- Tag tombstones never compact (client and hub).

## 7. Suggested execution order

1. **Tier 0 enablers** (Bus affinity contract + async resolver entry + worker/progress
   UI pattern) — small surface, retires whole classes, unblocks everything else.
2. **The §2 quartet** — fixes the week-long degradation for good; measurable win.
3. **Tier 2 user actions** (park/scrub, recording stop, timeline commit, option writes)
   — the daily-felt freezes, now cheap to fix on the Tier-0 rails.
4. **SDK hardening** (driver vocabulary export, threading contract, processor dispatch,
   widget contract completion) — before the extension ecosystem grows.
5. **Hub executor discipline + rollups on synced data** — viewer-side latency.
6. **Tier 3 long-tail** (git/zip/downloads on workers) + safety flags (§6) as they fit.

Items 1–3 together are the "performance milestone"; item 1 is where the responsiveness
UX ("what/why/how long") gets built exactly once.

## B. GUI-thread blocking paths (the responsiveness work-list)

### [CRITICAL | CONFIRMED] Session restore and option changes run driver I/O synchronously on the GUI thread, bypassing async_config
*core — `/home/kali/ferroDAC/ferrodac/core/manager.py:310`*

- **Impact:** Session restore applies every saved option and sink value as synchronous hardware I/O on the GUI thread, ignoring the async_config flag entirely. shelly_cloud sets async_config=True precisely because set_option does network calls (shelly_cloud.py:74, urlopen timeout=20 s per call, "a couple of (deliberately spaced) network calls") — an unreachable cloud freezes the app ~20-60 s at startup or on device rebind. Serial devices freeze for one transaction per option/sink (TPG: 0.6 s timeout each). For third-party drivers, the default (async_config=False) makes GUI-blocking the default behavior of the platform contract.
- **Trigger:** App start with a saved session; device replug (auto-rebind resolve pass); changing an option in the config dialog for any driver that didn't opt into async_config **Duration:** ms-600 ms per serial transaction; 20-60 s worst case for cloud drivers on network timeout, multiplied by the number of saved options + sink values **Feedback today:** None — no cursor, no status message; the window simply stops responding
- **Fix:** Route _apply_device_config through the same worker path as add/write (it already tolerates async via the 'later resolve pass' pattern), and make ALL set_option calls off-thread unconditionally — async_config then becomes a no-op flag kept only for API compatibility.
- **Verifier correction:** Two minor overstatements that do not change the verdict: (a) the worst-case single-driver freeze is ~41 s (20 s + 1.1 s + 20 s), so the "~20-60 s" range slightly overstates the upper bound; (b) the non-async branch of manager.set_option (l.205) does not "bypass" anything — it honors the documented opt-in contract (async_config=False means the driver declares set_option cheap), so that aside is design commentary rather than part of the defect. The actual defect is confined to _apply_device_config (session restore / rebind path).

### [CRITICAL | CONFIRMED] MoNA library download + MSP parse runs entirely on the GUI thread (minutes-long freeze)
*devices — `/home/kali/ferroDAC/ferrodac/ui/panels.py:1719`*

- **Impact:** The entire app freezes for the full download (up to 180 s timeout alone) plus a pure-Python regex parse of every spectrum block — realistically minutes. Same path at panels.py:1706 for import_msp on a user-chosen MSP file.
- **Trigger:** Gas composition panel -> gear config -> 'Download library' (or 'Import MSP…') **Duration:** 30 s to several minutes (network 30+180 s timeouts + regex parse of the archive + JSON save) **Feedback today:** Wait cursor only; window is unresponsive, no progress, no cancel
- **Fix:** Move download_library/import_msp onto a worker (the DeviceManager._run_async pattern or a QThread) with a progress dialog and cancel; parse in chunks off-thread and merge into LIBRARY on completion.
- **Verifier correction:** Two bounding facts worth adding, neither changing the verdict: (1) no data is lost during the freeze — device polling runs on plain threading.Threads (core/base.py:248) with timestamps captured at acquisition, and the bus inbox is an unbounded deque (core/bus.py:23) that flushes after the freeze; (2) the action is rare and explicitly user-initiated — _load_cache() (library.py:242) persists imports across restarts, so this is a one-time setup path, not a hot path. Also the 'multi-hundred-MB' size figure is unverified (plausibly tens-to-hundreds of MB), though the minutes-scale freeze conclusion holds independently via the network-timeout budget plus the pure-Python parse.

### [CRITICAL | CONFIRMED] StoreWriter runs all zarr appends on the GUI thread; each 2-s flush costs 65–110 ms due to 1 MiB-chunk tail RMW plus an uncached chunk-0 read per append
*foundations — `ferrodac/store/writer.py:109`*

- **Impact:** Measured: a 40-sample flush costs median 65–110 ms once an epoch exceeds ~0.5M samples (breakdown on a 0.9M store: tail-chunk RMW 52 ms + ta[0] chunk-0 read 13 ms + attrs 3 ms). With N sources that is N×~80 ms of GUI stall every 2 s for the entire run — chronic jank that directly violates the never-freeze goal; append_trace (zarrstore.py:329) does the same per-scan RMW for spectra. The needed write rate (≤400 samples/s ≈ 3 kB/s) is ~5 orders of magnitude below what zarr+SSD can sustain with sane usage — this is usage, not a stack limit.
- **Trigger:** Always-on during acquisition: every source flush (every 2 s or 4096 samples) **Duration:** 65–110 ms per source per flush, sawtoothing with tail-chunk fill; ~N×80 ms per 2 s for N sources **Feedback today:** none — perceived as ambient stutter
- **Fix:** Move StoreWriter behind a worker-thread queue (the Bus contract should let a sink declare 'run me off-thread'), shrink raw chunks to ~8–64k samples (64–512 kB) so a tail append rewrites kilobytes not megabytes, and cache t0 in memory instead of re-reading chunk 0 per append.
- **Verifier correction:** Minor quantitative nuances only: '1 MiB-chunk' is strictly 1 Mi-samples (= 8 MiB on disk; the claim's own 8 MB RMW figure is the consistent one), and steady-state append cost saw-tooths ~47-86 ms per 1M-sample chunk cycle on a favorable (tmpfs) box rather than a flat 65-110 ms — the claimed band is the upper half of the cycle and plausible on real laptop SSDs. Neither nuance changes kind, reachability, or severity.

### [CRITICAL | CONFIRMED] StoreWriter runs on the GUI thread; rollup rebuild reads the whole epoch and grows with session length
*historic-path — `ferrodac/store/writer.py:147`*

- **Impact:** Every 50k new samples per source, the GUI thread reads and re-downsamples the ENTIRE session epoch (one epoch per app session, writer.py:49). After a week at 10 Hz that is ~6M samples (~100 MB decompressed) per rebuild - a 0.5-3 s freeze recurring every ~80 min per source, growing linearly with uptime. On app close, store_writer.stop() (app.py:4274) rebuilds rollups for every source over all epochs: a multi-minute close freeze after long sessions.
- **Trigger:** Automatic: every ~50k samples per source during streaming; also every app close **Duration:** Grows with session length: sub-second early, seconds per source after a week; close can take minutes **Feedback today:** None (silent freeze); close looks like a hang
- **Fix:** Move StoreWriter to a real worker thread (it is already Qt-free), and make rollups incremental: append new buckets to existing pyramid levels instead of rebuilding from raw (the levels are append-only for an append-only epoch).
- **Verifier correction:** The close-freeze sub-claim is overstated in scope and magnitude: StoreWriter.stop() calls _rollup(key), which passes self._epoch (writer.py:152), so app close rebuilds only the CURRENT session's epoch per source — never 'all epochs'; prior sessions' history is untouched. The close stall (in closeEvent, app.py:4274, GUI thread) scales with session length, not total store history, and for a few sources is realistically seconds to tens of seconds after a week-long session, not multi-minute. This does not change the finding's severity, which rests on the fully-confirmed recurring in-session GUI freeze that grows without bound.

### [CRITICAL | CONFIRMED] Every park/scrub/go-live synchronously re-streams the full-resolution window through the bus on the GUI thread
*historic-path — `ferrodac/store/replay.py:293`*

- **Impact:** Triggered by scrub, ribbon drag release, jump-to-tag, zoom-to-recording, calendar jump, bookmark jump, and returning to live after a park. In default grow mode the window is [app-launch, now], so 'go live' after a park re-streams the ENTIRE session at full resolution: after days of streaming that is tens of millions of Python Reading objects (GBs of RAM) plus a sort - a freeze of tens of seconds to minutes, with the GUI only breathing via processEvents in the progress callback (app.py:4198). Play-steps re-stream the whole window per step with no progress at all (replay.py:277).
- **Trigger:** Any timeline navigation: scrub/park, jump-to-tag, zoom-to-recording, bookmark, calendar, go-live after park **Duration:** Seconds for hour-windows; minutes + multi-GB RAM for day/week windows **Feedback today:** Status-bar 'loading %' bar that pumps the event loop (parked loads only); nothing for play-steps or the go-live render
- **Fix:** Stream chunk-wise from a worker thread (read one time-chunk per source, merge incrementally - avoids materialising the whole window), and cap the re-stream to what panels can show (or feed charts via query() envelopes and reserve full-res re-stream for processors that need it).

### [CRITICAL | CONFIRMED] Store servicer runs blocking Zarr disk I/O directly on the hub event loop — every historic query stalls all live streams hub-wide
*hub — `server/hub/service.py:299`*

- **Impact:** The hub is a single asyncio loop carrying every Ingest session, live Subscribe fan-out, and doc collab room. While one client's Query/ReadRaw grinds through Zarr (worsened by the missing rollups, see next finding: full-epoch reads), every other user's live plot freezes and ingest backpressures. The requesting client's read tier then hits its 4 s deadline (ferrodac/net/readtier.py:28) and silently shows 'no remote coverage'. One user's export can freeze the whole lab's live view.
- **Trigger:** Any viewer panning/opening a plot resolved via the hub read tier; replay/analysis via read_raw/read_raw_trace; an agent reconnecting (GetSyncState); an agent pushing sync chunks (PushChunk). **Duration:** Typical 50–500 ms per RPC on warm data; worst multi-second (multi-GB epoch, cold cache, full-resolution ReadRaw of a week of history). Stalls are serialized, so concurrent queries queue. **Feedback today:** None. Other clients' live streams just stop updating; the requester silently gets an empty result after 4 s (error→empty in readtier).
- **Fix:** Apply the discipline BackupServicer already established: wrap every self.store.* call in await loop.run_in_executor(None, ...). ZarrStore calls are self-contained and Qt-free, so this is mechanical; add a small dedicated executor so a slow store can never exhaust the default pool shared with the backup mirror.
- **Verifier correction:** Two refinements, neither weakening the finding: (a) the Store service is inert when HUB_STORE_DIR is unset (store=None short-circuits to empty responses), but the store/sync/read-tier is a shipped, documented feature (DESIGN §7.4/§12.1), so the deployed configuration is affected; (b) the phrase 'every historic query stalls' is literally true only because the hub never builds rollups (apply_chunk never calls finalize_rollups) — if rollups existed hub-side, Query would be cheap and the everyday stall would come mainly from ReadRaw/ReadRawTrace (full-res + per-sample Python float conversion) and trace PushChunk (per-scan zarr resize+write loop), which block the loop regardless. The fix should both move store calls off the loop AND finalize rollups hub-side.

## D. Abstraction & interface debt

### [HIGH | CONFIRMED] BaseDevice/Device contract has no threading model — drivers are called from 4+ threads with no platform serialization
*core — `/home/kali/ferroDAC/ferrodac/core/base.py:260`*

- **Impact:** The Device contract IS the platform's public extension surface, and its concurrency rules exist only as tribal knowledge inside first-party drivers. A third-party driver that doesn't replicate TPG's _io_lock pattern gets interleaved serial transactions (corrupted ACK/ENQ protocols), racy _connect-vs-_read, and writes racing session-restore writes — bugs that appear only under load and get blamed on the driver. This is exactly the 'works for years while internals evolve' guarantee breaking.
- **Fix:** Give each device ONE owned executor thread: platform serializes _connect/_read/_write/set_option/check onto it (poll loop = the idle work of that thread). Document the contract in device.py: 'all _-hooks run on the device thread, never concurrently'. Drivers then need zero locks, and the manager's _OpWorker swarm collapses into per-device queues.

### [HIGH | PARTIAL] A fresh QThread is spawned per sink write on the high-rate routed control path — unordered and unbounded
*core — `/home/kali/ferroDAC/ferrodac/core/manager.py:179`*

- **Impact:** A source routed to a device sink at 10 Hz spawns 10 OS threads/second forever (thread create/destroy churn plus O(n) _workers.remove per completion). Worse: QThread start order does not guarantee execution order, and multiple writes run concurrently against one device — a setpoint ramp can arrive at hardware out of order, and concurrent writes interleave on stateful serial protocols. For the §18.1 control plane (bakeout heaters — safety-relevant) this is disqualifying.
- **Fix:** Replace thread-per-op with one long-lived per-device worker owning a bounded command queue (coalesce SETPOINT writes to latest-wins). This also becomes the single device executor recommended above.
- **Verifier correction:** Strike the sentence "concurrent writes interleave on stateful serial protocols": in-tree drivers (tpg256a, keithley6221, qms200) serialize every exchange with a per-device _io_lock, so interleaving/corruption is prevented; the hazard should be restated as (a) writes can be applied out of order (threads race on the lock, so a setpoint ramp can arrive reordered and the _sink_values cache in core/base.py:183 ends last-writer-wins-arbitrary) and (b) no queue/backpressure/coalescing means threads accumulate without bound when write rate exceeds device I/O latency. Note the lock is a per-driver convention, not a core Device-contract guarantee, so interleaving remains a latent risk only for lockless third-party/plugin drivers. Minor: the cited file is ferrodac/ui/workspace.py, not gui/workspace.py. High severity remains fair on the ordering + unbounded grounds for the intended 18.1 control plane.

### [CRITICAL | UNVERIFIED] Full-heap gc.collect() every 2 s scales linearly with live objects — a recurring GUI+GIL stall that grows all week
*gap — `/home/kali/ferroDAC/ferrodac/diagnostics.py:69`*

### [CRITICAL | CONFIRMED] 8 MiB append chunks: every flush is a read-modify-write that grows linearly for ~12 days — the week-long-slowdown signature
*store — `ferrodac/store/zarrstore.py:29`*

- **Impact:** Writing into a partial tail chunk makes zarr read+decode+re-encode+rewrite the whole chunk. One epoch per app session (writer.py:49), so at 1 Hz the tail chunk grows for ~12 days: hour 1 = ~29 KB per array (sub-ms); day 7 = 604,800 samples = ~4.8 MB per array. Each 2-second flush then costs ~24 MB of decode/encode (t RMW + v RMW + attrs['t0']=float(ta[0]) re-reading chunk 0 — the SAME growing chunk — every flush), i.e. ~30-100 ms per source, x20 sources, all on the GUI thread (see next finding). This grows monotonically over the first week and is the best mechanical match for 'after ~1 week the client becomes unresponsive even for size-independent actions'. It also poisons reads: any windowed read must decode at least one full 8 MiB chunk. Stack verdict: Zarr is fine (data volume at 1 Hz x 20 ch is ~830 MB/month), the chunking is wrong. Practical ceiling as-built: ~5-10 days continuous; with 4k-64k-sample chunks + write buffering: years.
- **Fix:** Right-size raw chunks to ~4,096-65,536 samples (matching the writer's own flush buffer), set attrs['t0'] only on first append instead of reading ta[0] every flush, and batch the four per-flush attribute writes (each rewrites zarr.json) into one update_attributes call.
- **Verifier correction:** The temporal profile is partly wrong in a way that makes the bug WORSE, not better: "hour 1 = ~29 KB per array (sub-ms)" is false. Zarr v3 pads the partial tail chunk to the full 8 MiB buffer and encodes all of it on every partial write, so a flush costs ~23 ms/source from the first minute; the week-scale growth is ~2-2.5x from that high base (23 -> 55 ms measured), not a from-zero linear ramp. So the mechanism predicts "janky from day 1, roughly doubling stall duty by day 7, then plateauing after ~12 days" (chunk 0, once full, still costs a full 8 MiB decode per flush via ta[0] forever) rather than "fine for a week, then collapses". It remains a primary mechanical contributor to the week-long slowdown, but is not by itself a clean from-nothing ramp; the reported from-fine-to-unresponsive signature likely needs the companion GUI-thread/rollup findings (finalize_rollups re-reads the FULL epoch every 50k samples — that one does grow O(N)) to fully account for the delta. The fix recommendation (4k-64k chunks + write buffering) stands.
